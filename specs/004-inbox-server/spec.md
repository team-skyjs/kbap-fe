## Clarifications

### Session 2026-09-16

- Q: 헤더 종 아이콘의 미읽음 배지는 "NEW" 필인가, 미읽음 개수 숫자인가? → A: 기존 "NEW" 필 고정. 미읽음 1건 이상이면 표시, 0이면 숨김. 숫자 표기 없음.
- Q: 알림함 항목 탭은 읽음만 하고 머무는가, 푸시 탭처럼 유형별 이동을 하는가? → A: 유형별 이동을 한다. BE가 목록·읽음 응답에 `type`(푸시 data.type과 같은 enum)·`foodId`(REVIEW_REMINDER만, 그 외 null)를 추가한다(FE→BE 요청 2026-09-16). 앱은 응답에 유형이 없거나 미지 유형이면 읽음 처리만 하고 알림함에 머문다.
- Q: 알림함 헤더의 "모두 읽음으로 표시" 버튼은? → A: 제거한다(전체 읽음 엔드포인트 없음 — 클라 반복 호출로 흉내 내지 않음). 문구 키도 함께 삭제.
- Q: 상대 시각 문구를 커뮤니티 화면의 공용 문구로 재사용하며 ko "방금"을 "방금 전"으로 바꿔도 되는가? → A: 된다(커뮤니티 글 시각도 "방금 전"으로 통일). 함께 zh-Hans·zh-Hant "N일 전" 문구의 불필요한 공백("{{count}} 天前")을 제거한다. 알림함 전용 키는 만들지 않는다.
- Q: 게스트가 알림함에 들어왔을 때 로그인 유도 시트 문구는 신규인가 재사용인가? → A: 시트를 띄우지 않는다. 게스트가 종 아이콘을 누르면 곧바로 로그인 화면으로 이동하고, 로그인 완료 시 알림함으로 복귀한다. 게이트 문구 신설 없음.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 회원이 알림함에서 서버에 기록된 알림을 본다 (Priority: P1)

회원이 헤더의 종 아이콘을 눌러 알림함을 열면, 이 기기로 최근 7일 안에 발송된 알림이 최신순으로 보인다. 앱이 꺼져 있을 때 도착한 알림도 빠지지 않는다. 각 항목은 발송 당시 이 기기 언어로 저장된 제목·본문을 그대로 보여준다.

**Why this priority**: 지금 알림함은 기기 로컬 기록이라 앱이 꺼진 동안 온 푸시가 남지 않고, 재설치하면 전부 사라진다. 서버가 알림 행을 기기 단위로 저장하므로 서버가 정본이다.

**Independent Test**: 관리자 테스트 발송으로 알림 2건을 보낸 뒤(1건은 앱 종료 상태에서), 알림함을 열어 2건이 최신순으로 보이면 통과.

**Acceptance Scenarios**:

1. **Given** 이 기기로 알림 3건이 발송됨(1건은 앱 종료 중), **When** 알림함 진입, **Then** 3건이 최신순으로 보인다.
2. **Given** 알림함 진입, **When** 서버에서 읽는 중, **Then** 로딩 스켈레톤이 보이고 빈 목록으로 위장하지 않는다.
3. **Given** 서버 읽기 실패, **When** 알림함 진입, **Then** 재시도 안내가 보이고 탭하면 다시 읽는다.
4. **Given** 최근 7일 알림이 없음, **When** 알림함 진입, **Then** 빈 상태 안내가 보인다.
5. **Given** 알림함이 열린 채 앱을 백그라운드로 보냈다가 복귀, **Then** 목록이 다시 읽혀 새 알림이 반영된다.
6. **Given** 알림함이 열린 상태에서 푸시 도착, **Then** 목록이 갱신되어 새 항목이 맨 위에 보인다.
7. **Given** 같은 회원이 다른 기기로 로그인, **When** 그 기기의 알림함 진입, **Then** 그 기기로 발송된 알림만 보이고 이 기기의 알림·읽음 상태는 보이지 않는다.

### User Story 2 - 알림 도착 시각이 상대 표기로 보인다 (Priority: P1)

각 알림 항목에 도착 시각이 "방금 전", "3분 전", "2시간 전", "1일 전"처럼 지금 기준 상대 표기로 보인다.

**Why this priority**: 알림함은 "놓친 것"을 확인하는 화면이라 얼마나 지났는지가 핵심 정보다. 현재는 리뷰 목록의 일 단위 표기(오늘/N일 전/N주 전)를 빌려 써서 당일 알림이 전부 "오늘"로 뭉개진다.

**Independent Test**: 도착 시각을 30초 전·5분 전·3시간 전·26시간 전·3일 전으로 둔 항목 5개를 렌더해 각각 "방금 전"·"5분 전"·"3시간 전"·"1일 전"·"3일 전"이 나오면 통과.

**Acceptance Scenarios**:

1. **Given** 도착 후 60초 미만, **Then** "방금 전".
2. **Given** 도착 후 1분 이상 60분 미만, **Then** "N분 전" (N = 경과 분, 내림).
3. **Given** 도착 후 1시간 이상 24시간 미만, **Then** "N시간 전" (N = 경과 시간, 내림).
4. **Given** 도착 후 24시간 이상, **Then** "N일 전" (N = 경과 일, 내림). 24시간~47시간은 "1일 전".
5. **Given** 앱 언어가 한국어 외, **Then** 같은 규칙이 그 언어 문구로 보인다(10개 언어).
6. **Given** 알림함을 열어 둔 채 시간이 흐름, **Then** 표기가 실시간으로 바뀌어야 할 의무는 없다. 화면 재진입·목록 갱신 시점의 값이면 충분하다.
7. **Given** 도착 시각이 기기 시계보다 미래(시계 오차), **Then** "방금 전"으로 표기한다.

### User Story 3 - 알림을 읽으면 읽음이 기기 단위로 기록되고 NEW 배지가 반영된다 (Priority: P1)

읽지 않은 알림은 강조 표시가 있고, 헤더 종 아이콘엔 미읽음이 1건 이상일 때 "NEW" 배지가 뜬다(개수 숫자 없음). 항목을 탭하면 읽음으로 바뀌며 서버에 기록되고, 미읽음이 0이 되면 배지가 사라지고, 알림 유형에 맞는 화면으로 이동한다. 푸시 알림 자체를 탭해 앱에 들어온 경우에도 그 알림은 읽음 처리된다.

**Why this priority**: 배지와 읽음 상태가 서버와 어긋나면 이미 본 알림이 계속 NEW로 남거나, 다른 기기에서 본 것이 여기서 미읽음으로 보이는 혼란이 생긴다. 계약상 읽음은 기기별이다.

**Independent Test**: 미읽음 2건 상태(NEW 배지) → 항목 1개 탭 → 미읽음 1(NEW 유지), 그 항목 강조 해제, 서버 조회 시 read=true → 다른 알림의 푸시를 탭해 진입 → 미읽음 0(배지 사라짐).

**Acceptance Scenarios**:

1. **Given** 미읽음 1건 이상, **When** 홈·음식·리뷰 탭 헤더를 봄, **Then** 종 아이콘에 "NEW" 배지가 보인다. 미읽음 0이면 배지가 없다.
2. **Given** 미읽음 항목, **When** 탭, **Then** 즉시 읽음 표시로 바뀌고 미읽음 수가 1 줄며(0이 되면 배지 소멸), 유형에 맞는 화면으로 이동한다.
3. **Given** 읽음 서버 기록이 실패, **When** 탭, **Then** 항목이 미읽음으로 되돌아가고 배지도 원복된다. 화면 이동은 그대로 진행된다.
4. **Given** 이미 읽은 항목, **When** 다시 탭, **Then** 상태 변화 없이 화면 이동만 한다.
5. **Given** 서버 알림 id가 실린 푸시, **When** 푸시를 탭해 앱 진입, **Then** 그 알림이 읽음 처리되고 배지가 반영된다.
6. **Given** 7일이 지나 목록에서 빠진 알림의 푸시, **When** 탭, **Then** 읽음 처리는 정상 수행되고 화면 이동도 정상이다.
7. **Given** 미읽음 항목과 읽음 항목, **Then** 두 행의 높이·패딩·보더 폭은 같고 색·강조만 다르다.

---

### User Story 4 - 게스트는 알림함 대신 로그인 화면으로 간다 (Priority: P2)

알림은 회원 전용이다. 게스트가 종 아이콘을 누르면 알림함 대신 곧바로 로그인 화면으로 이동하고 알림함 내용은 보이지 않는다. 로그인을 마치면 알림함으로 돌아온다. 게스트의 배지는 항상 0이다.

**Why this priority**: 알림함은 회원·기기 단위 서버 데이터라 게스트에겐 보여줄 것이 없다. 유도 시트 단계 없이 로그인 화면으로 직행한다(2026-09-16 결정).

**Independent Test**: 게스트로 종 아이콘 탭 → 로그인 화면, 알림 목록 미표시. 로그인 화면에서 뒤로 → 종 아이콘이 있던 화면. 로그인 완료 → 알림함 표시.

**Acceptance Scenarios**:

1. **Given** 게스트, **When** 종 아이콘 탭, **Then** 로그인 화면으로 이동하고 알림 목록은 한 순간도 렌더되지 않는다.
2. **Given** 로그인 화면(알림함에서 진입), **When** 뒤로 가기, **Then** 종 아이콘이 있던 화면으로 돌아간다.
3. **Given** 로그인 화면(알림함에서 진입), **When** 로그인 완료, **Then** 알림함이 열린다.
4. **Given** 게스트, **Then** 종 아이콘 배지가 표시되지 않는다(0).
5. **Given** 게스트 기기로 온 푸시, **When** 탭, **Then** 읽음 처리 없이 화면 이동만 한다.

---

### Edge Cases

- 로그아웃·탈퇴·다른 계정 로그인 직후 알림함을 열면 이전 계정의 목록·배지가 남아 있지 않아야 한다.
- 알림 도착과 동시에 사용자가 항목을 탭하면 읽음 처리와 목록 갱신이 겹쳐도 최종 상태는 서버 값이다.
- 목록 갱신 도중 읽음 처리 응답이 늦게 도착해도 최신 목록의 읽음 상태를 뒤집지 않는다.
- 두 항목을 연달아 탭해 요청이 겹쳐도 한 항목의 실패 원복이 다른 항목의 상태를 건드리지 않는다(항목 단위 원복).
- 서버가 7일 이내 알림을 많이 돌려줘도(수십 건) 한 번에 표시한다. 페이징·무한 스크롤은 없다.
- 기기 식별자가 없는 요청(설치 ID 누락)은 서버가 거부한다. 앱은 모든 요청에 설치 ID를 자동 첨부하므로 정상 경로에선 발생하지 않는다.
- 앱 언어를 바꾼 뒤 도착하는 알림은 서버가 새 언어로 저장하되, 이미 저장된 알림은 이전 언어 그대로다. 알림함은 서버 문자열을 그대로 보여준다.
- 기존 기기 로컬 알림 기록은 마이그레이션하지 않는다. 전환 후 알림함은 서버 목록만 보여준다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 알림함 목록은 서버에서 읽어야 한다. 기기 로컬 알림 기록(저장·조회·읽음)은 제거하고, 화면과 배지는 서버 목록만 사용한다.
- **FR-002**: 목록은 요청 기기로 발송된 최근 7일 이내 알림 전부이며 최신순이다. 항목은 서버가 저장한 제목·본문·도착 시각·읽음 여부를 그대로 쓴다. 앱이 문구 키로 제목을 만들지 않는다.
- **FR-003**: 목록 요청과 읽음 요청에는 기기 설치 식별자가 첨부되어야 한다(기존 공통 요청 경로가 자동 첨부).
- **FR-004**: 도착 시각은 현재 시각 기준 상대 표기로 보여야 한다. 60초 미만 "방금 전", 60분 미만 "N분 전", 24시간 미만 "N시간 전", 그 이상 "N일 전". N은 내림. 미래 시각은 "방금 전".
- **FR-005**: 상대 시각 문구는 10개 언어 모두에 존재해야 하며, 언어별 단수·복수 규칙을 따른다. 문구는 커뮤니티 화면의 기존 상대 시각 문구(방금/분/시간/일)를 공용으로 재사용한다 — ko "방금"은 "방금 전"으로 통일, zh-Hans·zh-Hant 일 단위 문구의 공백 제거. 알림함 전용 문구는 두지 않는다.
- **FR-006**: 헤더 종 아이콘 배지는 목록 중 읽지 않은 항목 수가 1 이상일 때 보이는 "NEW" 필이다(숫자 표기 없음, 기존 표시 유지). 별도 미읽음 조회는 없다. 게스트는 미읽음 0으로 배지 없음.
- **FR-007**: 항목 탭은 즉시 읽음 표시로 바꾸고 서버에 읽음을 기록한다. 실패 시 이전 상태로 되돌린다. 읽음 기록은 멱등이라 중복 탭이 오류가 아니다. 읽음은 항목 단위만 — 기존 "모두 읽음으로 표시" 버튼은 제거한다(전체 읽음 계약 없음).
- **FR-008**: 항목 탭 후 이동 화면은 기존 푸시 탭 이동 규칙과 같다(서버 응답의 알림 유형·foodId를 푸시 데이터와 같은 규칙으로 해석). 응답에 유형이 없거나 앱이 모르는 유형이면 이동하지 않고 알림함에 머문다(읽음 처리는 그대로).
- **FR-009**: 서버 알림 id가 실린 푸시를 탭해 앱에 진입하면 그 알림을 읽음 처리해야 한다. 게스트 기기에선 읽음 처리 없이 이동만 한다.
- **FR-010**: 목록은 앱 시작·포그라운드 복귀·포그라운드 푸시 수신·푸시 탭에서 다시 읽어야 한다. 항목 읽음 처리는 개별 항목 단위로 앱이 관리한다 — 성공 시 서버가 돌려준 그 항목으로 교체, 실패 시 그 항목만 이전 상태로 되돌린다. **읽음 처리 뒤 목록을 다시 읽지 않는다**(2026-09-17 결정: 서버 상태와 잠시 어긋날 수 있음을 수용, 다음 재조회 시점에 맞춰짐).
- **FR-011**: 로그인·로그아웃·탈퇴 경계에서 알림함 목록과 배지가 이전 계정 값을 남기지 않아야 한다.
- **FR-012**: 게스트가 알림함 경로에 도달하면 로그인 화면으로 곧바로 이동하고 목록은 렌더되지 않아야 한다(유도 시트 없음). 로그인 화면에서 뒤로 가기는 이전 화면 복귀, 로그인 완료 시 알림함으로 복귀.
- **FR-013**: 로딩 중 스켈레톤, 실패 시 재시도 안내, 0건 시 빈 상태를 보여야 한다. 빈 목록으로 위장하지 않는다.
- **FR-014**: 읽음/미읽음 행은 레이아웃 치수가 같고 색·강조만 달라야 한다.
- **FR-015**: 기존 로컬 알림함 테스트 스위트는 서버 기반 스위트로 대체한다.

### Key Entities

- **알림(서버 정본)**: 이 기기로 발송된 알림 한 건. 식별자 · 유형(푸시 유형과 같은 집합) · 음식 식별자(리뷰 리마인더만, 그 외 없음) · 제목(발송 시점 언어) · 본문 · 도착 시각 · 읽음 여부. 회원 + 기기 단위로 존재하며 7일 후 목록에서 제외.
- **미읽음 수**: 목록 중 읽음 여부가 거짓인 항목 수. 파생값.
- **상대 시각 표기**: 도착 시각과 현재 시각의 차이를 4단계(방금/분/시간/일)로 문구화한 값.
- **기기 설치 식별자**: 알림함의 범위를 정하는 키. 회원이 아니라 기기 귀속.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 앱 종료 상태에서 도착한 알림이 알림함에 100% 나타난다(실기기 테스트 발송).
- **SC-002**: 상대 시각 경계값(59초·60초·59분·60분·23시간·24시간·47시간·48시간·미래) 9개가 유닛에서 기대 문구와 일치한다.
- **SC-003**: 10개 언어에서 상대 시각 4종 문구가 누락 없이 존재한다(키 패리티 유닛).
- **SC-004**: 항목 탭 후 미읽음 수 감소(마지막 1건이면 NEW 배지 소멸)가 즉시 반영되고, 서버 실패 시 100% 원복된다(유닛).
- **SC-005**: 게스트가 알림함 경로에서 목록을 보는 경우 0건, 게스트 배지 0.
- **SC-006**: 기기 2대로 같은 회원 로그인 시 각 기기가 자기 알림·자기 읽음 상태만 본다(실기기).
- **SC-007**: 기기 로컬 알림 기록 코드·저장 키가 남지 않는다(소스 검사).
- **SC-008**: 타입 검사 0 오류, 전체 테스트 통과. JS 전용 변경.

## Assumptions

- 서버 계약은 확정 상태다(목록: 파라미터 없음·7일·최신순, 읽음: 항목 단위 멱등). 커서 페이징·전체 읽음·미읽음 수 조회는 만들지 않는다.
- 알림함과 읽음은 기기 단위다. 같은 회원의 다른 기기 알림·읽음이 안 보이는 것은 수용한다.
- 서버 목록·읽음 응답에 알림 유형과 리마인더 음식 식별자가 포함된다(BE 확장 요청 2026-09-16, dev 배포 후 계약 재확인). 배포 전이거나 필드가 비어 있으면 항목 탭은 읽음 처리 + 알림함 유지로 동작한다. 푸시 탭 이동은 기존 규칙 그대로.
- 상대 시각 표기는 화면 렌더 시점 기준이며 초 단위 갱신 타이머는 두지 않는다.
- 게스트 처리는 로그인 화면 직행이라 게이트 문구를 새로 만들지 않는다(2026-09-16 결정).
- 기존 로컬 알림 기록과 로컬 리뷰 리마인더 폐기(별도 작업)는 함께 정리될 수 있다. 이 작업은 알림함 로컬 기록만 책임진다.
- 푸시·알림함 언어는 토큰 등록 시 보고한 기기 언어로 서버가 정한다. 언어 변경 시 토큰 재등록은 이미 구현되어 있다.
