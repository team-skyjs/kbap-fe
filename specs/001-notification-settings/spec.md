# Feature Specification: 알림 설정 2그룹 재편 + 서버 정본화

**Feature Branch**: `001-notification-settings`

**Created**: 2026-09-11

**Status**: Draft

**Input**: User description: "497 워크트리로 진행" — Jira KB-497 「[FE] 알림 설정 화면 2그룹 재편 + 서버 정본화 — GET/PATCH /api/notifications/settings, 광고성 동의 2종 문구」

## Clarifications

### Session 2026-09-11

- Q: 알림 동의 단위는? → A: **기기 단위.** 같은 계정으로 다른 기기를 쓰면 그 기기에서 별도로 동의를 받는다. 회원 단위 공유 아님. (⚠️ 현행 dev Swagger `GET/PATCH /api/notifications/settings`는 "회원의 알림 설정"으로 정의되어 있어 BE 계약 변경이 선행되어야 한다 — 아래 Dependencies.)
- Q: 푸시·광고성 동의를 받는 시점은? → A: **온보딩 직후 홈 화면 첫 진입 시** 한 표면에서 푸시 알림(OS 권한) 동의와 광고성 푸시 동의(2종)를 함께 받는다. 온보딩 제출 직후 모달은 이 시점으로 이동.
- Q: 메뉴 스캔 후 뜨는 "리뷰 알림 받을래요?" 문의 화면은? → A: **유지.** (현행 스캔 결과 표면의 푸시 프라이머.)
- Q: 알림 문구 번역은 누가? → A: **서버.** 앱은 토큰 등록 시 현재 언어 설정을 항상 함께 보낸다(앱 시작·언어 변경 시 갱신). 알림 제목·본문은 서버가 언어별로 구성하며 앱은 문구를 갖지 않는다.
- Q: BE 계약 방향? → A: **회원만 알림을 받도록 BE를 수정한다**(2026-09-11 종한). 게스트 토큰 `settings` 동의 경로는 폐기 대상. 설정은 회원×기기(`X-Installation-Id`) 단위 — FE는 이미 전 요청에 이 헤더를 보내므로 헤더 추가 작업 없음.
- Q: BE "회원 전용" 수정의 FE 영향? → A: BE 세션 통보(2026-09-11, 종한 전달): **유일한 외부 영향 = 토큰 등록을 로그인 완료 뒤로 옮겨야 한다.** 게스트 상태의 `PUT /api/notifications/tokens`는 더 이상 유효하지 않다. FE는 세션이 있을 때만 토큰을 등록하고, 로그인 성공 직후 1회 등록한다.
- Q: 온보딩 직후 홈 통합 표면(A안)? → A (2026-09-11 종한): **제외.** 온보딩 직후 프라이머 모달도 제거. OS 권한은 스캔 후 프라이머 시트 1곳, 광고성 동의는 설정 화면 토글 → 시트.
- Q: 소식(NEWS) 알림 유형 추가(KB-498 9/11 갱신·KB-544 기기 토글 `news`)? → A (2026-09-11 종한): 「K-Bap 소식」 그룹에 **「소식 알림」 토글을 추가**한다. 동의 시트의 진입점은 이 토글(OFF→ON)이며, 「식사 시간 알림」은 하위 토글로 소식이 꺼져 있으면 비활성(흐림). 문구는 Codex UX 리라이트로 단문화(섹션 설명 삭제, 한 줄 부제).
- Q: 설정 단위 최종? → A (2026-09-11 종한 확정, BE KB-544 등록): **알림 설정 토글(activity·mealTime·news)은 (회원, 기기) 단위**, **광고성 동의 원장은 회원 단위**. 같은 계정의 다른 기기는 토글이 별개지만 동의는 한 번 하면 회원 전체에 유효. KB-543(#260) 머지 후 KB-544 착수, 그 전까지 dev는 현행 회원 단위.
- Q: 설정 화면에서 광고성 동의를 어떻게 받나? → A (2026-09-11 종한): **설정 화면에 동의 체크 항목을 노출하지 않는다.** 「식사 시간 알림」 토글만 두고, 동의가 없는 상태에서 토글을 켜면 **하단 시트**가 올라와 동의 2종(체크 + 전문 링크)을 받는다. 시트에서 둘 다 체크 후 확인 → 소식 켜짐(버전 2종 저장) → 토글 ON. **토글 OFF = 이 기기의 식사 시간 알림만 끔(`news.mealTime:false`) — 동의는 철회되지 않는다**(2026-09-11 종한 정정). 동의 상태(일시·버전·전문 보기)는 토글 아래 캡션으로만 표시. 동의 철회 UI는 이번 범위 밖. 피그마 시안: 「KB-497 알림 설정 시안」 페이지 1·1b·3.
- Q: 동의 전문 표시 방식(FR-009)? → A: 기본안 채택 — kbap-legal 정적 페이지를 인앱 브라우저로 열기(로그인 약관 링크 선례). 페이지 2개 생성은 kbap-legal 레포 요청.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 회원이 이 기기의 알림 설정을 서버에 저장하고 같은 값을 본다 (Priority: P1)

회원이 프로필 > 알림 설정에 들어가면 **이 기기**에 대해 서버에 저장된 현재 설정이 보인다. 토글을 바꾸면 즉시 화면에 반영되고 서버에 저장된다. 저장에 실패하면 이전 값으로 되돌아가고 실패 안내가 뜬다. 설정과 동의는 기기(앱 설치 ID) 단위다 — 같은 계정으로 다른 기기에 로그인하면 그 기기는 전부 꺼짐에서 시작하고 별도로 동의를 받는다.

**Why this priority**: 정본이 기기 로컬(AsyncStorage)에 있으면 표시·실제 발송이 어긋나고 동의 기록(버전·시각)이 남지 않는다. 광고성 동의는 법적 기록이라 서버 정본이 전제 조건이다. 동의 단위가 기기인 이유는 푸시 토큰이 기기 귀속이며 OS 권한도 기기별이기 때문이다.

**Independent Test**: 회원 계정으로 설정 화면 진입 → 토글 변경 → 화면 재진입 시 변경값 유지 → 같은 계정으로 다른 기기 로그인 → 그 기기는 전부 꺼짐이면 통과.

**Acceptance Scenarios**:

1. **Given** 이 기기에서 설정을 한 번도 바꾼 적 없음, **When** 알림 설정 화면 진입, **Then** 모든 토글이 꺼짐으로 표시된다(서버 기본값).
2. **Given** 기기 A에 활동 푸시 켜짐이 저장됨, **When** 기기 B에서 같은 계정으로 화면 진입, **Then** 기기 B는 전부 꺼짐으로 표시된다(기기별 독립).
3. **Given** 화면이 열려 있음, **When** 활동 푸시 토글을 누름, **Then** 스위치가 즉시 바뀌고 서버 저장이 완료되면 그 값이 유지된다.
4. **Given** 서버가 저장 요청을 거부함(네트워크 오류 등), **When** 토글을 누름, **Then** 스위치가 원래 값으로 돌아가고 "저장하지 못했어요" 안내가 보인다.
5. **Given** 서버에서 설정을 읽는 중, **When** 화면 진입, **Then** 기본값 스위치로 위장하지 않고 로딩 스켈레톤이 보인다.
6. **Given** 설정 읽기가 실패함, **When** 화면 진입, **Then** 스위치를 보여주지 않고 재시도 안내가 보이며, 탭하면 다시 읽는다.

### User Story 2 - 회원이 소식 알림 토글로 광고성 소식을 켜고 끈다 (Priority: P1)

「K-Bap 소식」 그룹에는 「소식 알림」 토글과 하위 「식사 시간 알림」 토글이 보인다(동의 체크 항목은 화면에 노출하지 않는다). 소식이 꺼진 상태에서 「소식 알림」을 켜면 하단 시트가 올라와 「마케팅 목적 개인정보 수집·이용 동의(선택)」와 「광고성 정보 수신 동의(선택)」 두 체크 항목과 전문 링크를 보여준다. 둘 다 체크하고 확인하면 소식 알림이 켜지고(식사 시간 알림도 함께 켜짐) 토글이 ON이 된다. 「식사 시간 알림」은 소식이 켜진 동안만 조작 가능하며 끄면 이 기기의 식사 시간 알림만 꺼진다. 「소식 알림」을 끄면 이 기기의 소식 수신만 꺼진다(서버는 회원의 모든 기기가 꺼졌을 때만 동의 원장을 닫는다 — KB-544). 동의 상태(일시·버전)와 전문 보기는 그룹 아래 캡션으로 표시된다.

**Why this priority**: 광고성 알림은 두 동의 없이 보내면 안 되며, 동의 버전과 시각이 서버에 기록되어야 한다. 현재 화면의 「메뉴 스캔 알림」 문구는 점심 스캔 한정이라 광고성 동의로 쓸 수 없다.

**Independent Test**: 소식 꺼진 기기에서 「소식 알림」 탭 → 시트 → 두 동의 체크 → 확인 → 소식·식사 시간 ON + 캡션 → 「식사 시간 알림」 OFF → `news.mealTime:false`, 소식 ON 유지 → 「소식 알림」 OFF → `news.enabled:false`, 식사 시간 비활성·캡션 사라짐이면 통과.

**Acceptance Scenarios**:

1. **Given** 소식 알림 꺼짐, **When** 「소식 알림」 토글을 누름, **Then** 토글은 OFF 그대로이고 동의 시트가 하단에서 올라온다(체크 2개 모두 미체크, 확인 버튼 비활성).
2. **Given** 시트에서 동의 하나만 체크, **When** 확인 버튼을 봄, **Then** 비활성이며 서버 요청이 없다.
3. **Given** 시트에서 두 동의 모두 체크, **When** 「동의하고 알림 켜기」를 누름, **Then** 소식 알림이 켜지고(버전 2종 저장, 식사 시간 알림도 켜짐) 시트가 닫히며 「소식 알림」 ON, 캡션에 동의 일시·버전이 보인다.
4. **Given** 시트가 열림, **When** 「나중에」 또는 바깥 탭, **Then** 시트가 닫히고 토글은 OFF, 서버 변화 없음. 다시 토글을 누르면 시트가 다시 뜬다(재노출 제한 없음).
5. **Given** 소식 알림 켜짐, **When** 「식사 시간 알림」을 끔, **Then** 이 기기의 식사 시간 알림만 꺼진다(`news.mealTime:false`). 소식·동의·캡션은 유지된다.
6. **Given** 소식 알림 켜짐·식사 시간 알림 꺼짐, **When** 「식사 시간 알림」을 켬, **Then** 시트 없이 식사 시간 알림만 켜진다(`news.mealTime:true`).
9. **Given** 소식 알림 켜짐, **When** 「소식 알림」을 끔, **Then** 이 기기의 소식 수신이 꺼지고(`news.enabled:false`) 「식사 시간 알림」은 OFF·비활성으로 보이며 캡션이 사라진다.
10. **Given** 소식 알림 꺼짐, **When** 「식사 시간 알림」(비활성)을 누름, **Then** 아무 변화가 없다.
7. **Given** 시트 또는 캡션의 전문 열람 진입점, **When** 누름, **Then** 해당 동의 전문이 현재 앱 언어로 표시된다.
8. **Given** 동의 문구가 개정되어 버전이 올라감, **When** 이전 버전에 동의한 회원이 화면 진입, **Then** 서버에 저장된 동의 상태가 그대로 표시된다(재동의 강제는 이번 범위 밖).

### User Story 3 - 게스트는 알림 설정에 들어갈 수 없다 (Priority: P2)

알림은 회원 전용이다. 게스트가 프로필 탭에서 알림 설정 진입점을 보지 못하며, 딥링크로 설정 화면에 도달해도 로그인 안내 시트가 뜨고 설정 내용은 보이지 않는다.

**Why this priority**: 설정의 유일한 정본이 서버이므로 게스트 로컬 설정은 존재할 수 없다. 딥링크 이중 방어는 저장된 북마크 화면과 같은 선례를 따른다.

**Independent Test**: 게스트 상태에서 설정 화면 딥링크 진입 → 로그인 안내 시트가 뜨고 토글이 없으면 통과.

**Acceptance Scenarios**:

1. **Given** 게스트, **When** 프로필 탭 열람, **Then** 알림 설정 진입 행이 없다.
2. **Given** 게스트, **When** 설정 화면 딥링크로 진입, **Then** 로그인 안내 시트가 뜨고 토글·동의 항목이 렌더되지 않는다.
3. **Given** 게스트가 로그인 안내 시트에서 로그인 완료, **When** 설정 화면으로 돌아옴, **Then** 서버 설정이 표시된다.

### User Story 4 - 온보딩 직후에는 알림 요청이 뜨지 않고, 첫 스캔 후에 한 번 받는다 (Priority: P2)

온보딩을 마치고 홈에 들어와도 알림 동의 표면은 뜨지 않는다(2026-09-11 종한 결정 — 홈 통합 표면 A안 제외, UX 리서치 권고). OS 알림 권한은 첫 스캔 결과 직후 하단 시트(US6)에서 한 번 요청하고, 광고성 동의는 설정 화면의 식사 시간 알림 토글(US2)에서 받는다.

**Why this priority**: 가치 경험 전 요청은 iOS 1회성 프롬프트를 최저 동의율 시점에 소진하고, 법정 동의를 OS 권한과 한 표면에 섞으면 번들 인상을 준다.

**Independent Test**: 신규 회원 온보딩 완료 → 홈 진입 시 어떤 알림 표면도 뜨지 않음 → 첫 스캔 결과에서 프라이머 시트가 뜨면 통과.

**Acceptance Scenarios**:

1. **Given** 온보딩 제출 성공, **When** 홈 진입, **Then** 알림 관련 모달·시트가 뜨지 않는다.
2. **Given** 온보딩 제출 성공 직후, **When** 화면 전환, **Then** 기존 온보딩 프라이머 모달도 뜨지 않는다(제거).

### User Story 6 - 메뉴 스캔 후 "리뷰 알림 받을래요?" 문의는 그대로 유지된다 (Priority: P2)

스캔 결과 화면에서 처음 뜨는 알림 안내(리뷰 리마인더 목적)는 현행대로 유지된다. 수락 → OS 권한 허용 시 토큰이 등록되고 활동 푸시 켜짐이 저장된다. 게스트가 수락하면 OS 권한만 얻고(노출 기록), 토큰 등록·설정 저장은 로그인 완료 뒤에 이뤄진다. 이 표면은 기기당 1회다.

**Independent Test**: 홈 동의 표면을 보지 않은 상태(예: 기존 회원 업데이트)에서 첫 스캔 완료 → 문의 표시 → 수락 → 설정 화면에서 활동 푸시 켜짐이면 통과.

**Acceptance Scenarios**:

1. **Given** 이 기기에서 알림 안내를 본 적 없음, **When** 첫 스캔 결과 표시, **Then** 리뷰 알림 문의가 뜬다.
2. **Given** 이 기기에서 프라이머를 이미 봤음(수락/거절 기록), **When** 첫 스캔 결과 표시, **Then** 문의가 뜨지 않는다.
3. **Given** 문의 표시, **When** 수락 → OS 권한 허용, **Then** 활동 푸시 켜짐이 저장된다.

### User Story 5 - OS 알림이 꺼져 있으면 안내와 설정 앱 바로가기가 보인다 (Priority: P3)

기기 시스템 설정에서 K-Bap 알림이 꺼져 있으면 설정 화면 상단에 안내 배너가 뜨고, 누르면 시스템 설정 앱이 열린다. 앱으로 돌아오면 권한 상태가 다시 확인된다.

**Why this priority**: 기존 동작 유지. 앱 설정이 켜져 있어도 OS가 막으면 알림이 오지 않으므로 사용자가 원인을 알아야 한다.

**Independent Test**: OS 알림 거부 상태로 화면 진입 → 배너 표시 → 탭 → 시스템 설정 열림 → 복귀 시 재확인되면 통과.

**Acceptance Scenarios**:

1. **Given** OS 알림 권한 거부됨, **When** 화면 진입, **Then** 상단에 "시스템 설정에서 K-Bap 알림이 꺼져 있어요" 배너와 바로가기가 보인다.
2. **Given** 배너 표시, **When** 시스템 설정에서 알림을 켜고 앱으로 복귀, **Then** 배너가 사라진다.

---

### Edge Cases

- 소식 알림이 꺼진 상태에서 식사 시간 알림만 켜 달라는 요청이 서버에 도달하면 서버가 거부한다. 화면은 이 조합을 만들 수 없어야 하며, 만약 거부 응답이 오면 이전 값으로 되돌리고 실패 안내를 보인다.
- 소식 알림을 켜는 요청에 동의 버전이 빠지면 서버가 거부한다. 화면은 항상 두 버전을 함께 보내야 한다.
- 토글을 빠르게 연타하면 마지막 요청 결과가 화면에 반영되어야 하고, 중간 응답이 최신 값을 덮어쓰면 안 된다.
- 세션이 만료된 채 토글하면 저장이 거부된다. 화면은 실패 안내 후 이전 값으로 돌아가고, 재로그인 후에는 서버 값을 다시 읽는다.
- 오프라인 상태에서 화면 진입 시 로컬 캐시가 없으면 읽기 오류 상태(재시도 안내)가 보인다.
- 탈퇴 후 재가입한 회원은 전부 꺼짐(서버 기본값)으로 시작한다. 이전 기기에 남은 로컬 설정은 참조하지 않는다.
- 계정 전환(애플↔구글) 시 이전 계정의 설정이 화면에 남지 않고 새 계정의 서버 값이 표시된다.
- 프라이머 허용 직후 사용자가 설정 화면으로 이동해 활동 푸시를 바로 끄면, 늦게 도착한 프라이머 저장 응답이 켜짐으로 되돌리지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 알림 설정 화면은 회원에게 두 그룹을 보여야 한다. ① 「내 활동 알림」: 「활동 알림」 토글 1개(리뷰 반응·리뷰 리마인더 통합). ② 「K-Bap 소식」: 「소식 알림」 토글(NEWS·SCAN_SUGGESTION 등 광고성 소식) + 하위 「식사 시간 알림」 토글 + (소식 켜진 상태일 때) 동의 일시·버전·전문 보기 캡션. **동의 체크 항목은 설정 화면에 노출하지 않는다.** 섹션 설명 문장 없음, 부제는 한 줄(Codex 리라이트 2026-09-11).
- **FR-002**: 설정 값의 유일한 정본은 서버여야 한다. 화면 진입 시 서버에서 읽고, 변경 시 서버에 저장한다. 기기 로컬에 설정 값을 별도 저장하지 않는다. **설정 토글(activity·news·mealTime)의 단위는 (회원, 기기)** 이고 **광고성 동의 원장은 회원 단위**다(KB-544) — 모든 설정 읽기·쓰기 요청에 기기 식별자를 실어 보내며, 토글은 같은 회원의 다른 기기 값과 섞이지 않는다. 화면의 소식 ON 표시는 서버 계산값(`news.enabled` = 이 기기 토글 AND 회원 동의)을 그대로 쓴다.
- **FR-003**: 기존 기기 로컬 알림 설정(3토글 저장소·넛지 동의 시각)과 게스트 로컬 동의 저장소는 제거해야 한다. 앱 업데이트 후 남은 값은 읽지 않는다.
- **FR-004**: 토글·체크 변경은 화면에 즉시 반영되고, 서버 저장 실패 시 이전 값으로 되돌리며 실패 안내를 표시해야 한다. 저장 성공 응답은 서버가 돌려준 전체 설정으로 화면 상태를 교체한다.
- **FR-005**: 소식 알림은 두 동의(마케팅 목적 개인정보 수집·이용 동의, 광고성 정보 수신 동의)가 모두 체크된 경우에만 켜져야 한다. 켤 때 두 동의의 현재 문구 버전을 함께 서버에 보낸다. 동의는 **「소식 알림」 토글을 켤 때 올라오는 하단 시트**에서 받는다(체크 2개 + 전문 링크 + 확인/나중에). 확인 버튼은 둘 다 체크된 경우에만 활성. 시트 표시 조건은 `news.enabled === false`(회원 동의 존재 여부와 무관 — 서버가 같은 버전이면 무변화 처리).
- **FR-006**: 소식 알림을 켜면(`news.enabled:true`) 식사 시간 알림도 함께 켜진다(서버가 하위 토글을 켬).
- **FR-007**: 「식사 시간 알림」을 끄면 **이 기기의 식사 시간 알림만** 끈다(`news.mealTime:false`). 소식·동의·캡션은 유지. 「소식 알림」을 끄면 `news.enabled:false`(이 기기 소식 OFF — 원장 철회 여부는 서버 규칙: 회원 전 기기 OFF 시에만). FE에 별도 동의 철회 UI는 없다.
- **FR-008**: 소식 알림이 꺼진 동안 「식사 시간 알림」은 OFF·비활성(색·불투명도만, 탭 무동작). 「소식 알림」 OFF→ON 탭은 서버 요청 없이 시트만 띄우고, 시트 확인 전까지 토글은 OFF를 유지한다. 소식이 켜진 상태에서 「식사 시간 알림」 ON은 `news.mealTime:true`.
- **FR-009**: 각 동의 항목은 전문 열람 진입점을 가져야 하며, 전문은 현재 앱 언어로 표시된다. 전문 표시 방식: 로그인 화면 약관 링크 선례대로 **kbap-legal 정적 페이지를 인앱 브라우저로 연다**(plan research R1, 2026-09-11 기본안 채택). 로케일 대응은 페이지 몫.
- **FR-010**: 동의 문구 2종은 앱이 지원하는 10개 언어 전부에 존재해야 하며, 한국어 문구는 별도 검수를 거친다. 문구를 바꾸면 해당 동의의 버전 번호(양의 정수)를 올린다.
- **FR-011**: 기존 「메뉴 스캔 알림」「리뷰 반응」「리뷰 작성 알림」「야간 광고성 정보 수신 동의」 문구는 새 구성에 맞게 정리(제거 또는 교체)해야 하며, 10개 언어 키 집합이 일치해야 한다.
- **FR-012**: 게스트는 프로필 탭에 알림 설정 진입점이 보이지 않아야 하고, 딥링크로 설정 화면에 도달하면 로그인 안내 시트가 뜨며 설정 내용은 렌더되지 않아야 한다.
- **FR-013**: 온보딩 제출 직후와 홈 첫 진입에는 알림 동의 표면을 띄우지 않는다(기존 온보딩 프라이머 모달 제거).
- **FR-018**: 스캔 결과 화면의 첫 알림 문의(리뷰 알림)는 **하단 시트**로 기기당 1회 뜬다(코치마크와 직렬화 유지). 「알림 켜기」 → OS 권한 → 허용 시 토큰 등록(세션 있을 때) + 회원이면 활동 푸시 켜짐 저장. 「나중에」 = 노출 기록만.
- **FR-019**: 토큰 등록 요청에는 항상 앱의 현재 언어 설정을 함께 보내야 한다(앱 시작·언어 변경·권한 획득 시 갱신). 알림 제목·본문은 서버가 언어별로 구성하며, 앱은 알림 문구를 보유·번역하지 않는다.
- **FR-020**: 토큰 등록은 **회원 세션이 있을 때만** 보낸다(게스트 요청 0). 로그인(세션 교환) 성공 직후 1회 등록하고, 앱 시작·언어 변경·권한 획득 시의 등록도 세션 유무를 먼저 확인한다. 로그아웃·탈퇴 후에는 등록하지 않는다. 401 등 등록 실패는 앱 동작을 막지 않고 무시한다(비치명 로그). 요청 본문은 `token`·`platform`·`lang` 3개뿐이며 `settings` 객체는 보내지 않는다. (BE KB-543, kbap-server#260)
- **FR-014**: OS 알림 권한이 거부된 상태면 화면 상단에 안내 배너와 시스템 설정 바로가기를 보여야 하며, 앱 복귀 시 권한 상태를 다시 확인한다.
- **FR-015**: 설정 읽는 중에는 로딩 스켈레톤을, 읽기 실패 시에는 값 없이 재시도 안내를 보여야 한다. 기본값 스위치로 위장하지 않는다.
- **FR-016**: 상태 전환(켜짐/꺼짐/비활성/체크)은 색·불투명도만 바꾸고 높이·패딩·보더 폭·라운딩 등 레이아웃 치수는 바꾸지 않아야 한다.
- **FR-017**: 스캔 프라이머 시트를 이미 보여줬는지의 기록은 기기에 남긴다(기기 귀속, 현행 키 유지). 설정 값과 달리 서버로 옮기지 않는다.

### Key Entities

- **알림 설정(서버 정본)**: 회원 × 기기(앱 설치 ID)당 1개. 활동 푸시 여부 · 소식 알림 여부 · 식사 시간 알림 여부 · 마케팅 개인정보 동의(버전·시각, 없을 수 있음) · 광고성 수신 동의(버전·시각, 없을 수 있음). 설정이 없는 회원은 전부 꺼짐으로 취급된다.
- **동의 문구 버전**: 마케팅 개인정보 동의 버전, 광고성 수신 동의 버전. 앱에 정수 상수로 존재하며 문구 개정 시 증가. 서버는 동의 시 이 버전을 기록한다.
- **OS 알림 권한 상태**: 허용/거부/미결정. 서버 설정과 독립이며 기기가 정본.
- **동의 표면 표시 기록**: 알림 동의 안내(홈·스캔)를 이 기기에서 보여줬는지. 기기 로컬.
- **기기 언어**: 토큰 등록 시 서버에 저장되는 앱 현재 언어. 서버가 알림 문구 번역에 사용.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 설정 화면에 표시되는 값이 서버 응답과 100% 일치하고, 기기 로컬 저장소에서 읽은 설정 값이 0건이다. 같은 계정의 다른 기기 값이 이 기기에 표시되는 경우가 0건이다.
- **SC-002**: 토글 조작 후 화면 반영까지 체감 지연이 없고(즉시), 서버 저장 결과가 2초 안에 확정된다(실패 시 되돌림 포함).
- **SC-003**: 두 동의 없이 소식 알림이 켜지는 경로가 화면상 존재하지 않는다(시트 확인 버튼 활성 조건·PATCH 본문 유닛 검증 통과).
- **SC-004**: 소식 켜진 상태에서 식사 시간 알림 OFF→ON 왕복에 시트가 뜨지 않고 캡션이 유지된다. 소식 OFF→ON은 시트를 거친다(유닛 + 실기).
- **SC-005**: 게스트가 설정 화면 딥링크로 진입했을 때 토글이 노출되는 경우가 0건이다.
- **SC-006**: 스캔 프라이머에서 푸시를 허용한 회원의 활동 푸시가 별도 조작 없이 켜짐으로 저장된다. 온보딩 직후 홈에서 알림 표면이 뜨는 경우가 0건이다.
- **SC-010**: 토큰 등록 요청 100%에 현재 언어 코드가 포함되고, 언어 변경 후 재등록된다(유닛 검증).
- **SC-011**: 게스트 상태에서 발생하는 토큰 등록 요청이 0건이고, 로그인 성공 직후 등록이 1회 발생한다(유닛 검증).
- **SC-007**: 동의 문구·라벨이 10개 언어 모두 누락 없이 존재하고 구 문구 키가 남지 않는다.
- **SC-008**: 상태 전환 전후 레이아웃 치수가 동일함이 유닛 테스트로 보장된다.
- **SC-009**: 타입 검사 0 오류, 전체 테스트 통과.

## Dependencies (BE 계약 — BE 수정 예정, 2026-09-11 결정)

- **회원 전용 + 기기 단위 설정**: BE가 "회원만 알림 수신"으로 수정한다. 그에 따라 `GET/PATCH /api/notifications/settings`는 `X-Installation-Id`를 키로 회원×기기 단위로 읽고 쓰는 것으로 가정한다(현행 dev Swagger는 회원 단위·헤더 선택 — 변경 전). FE는 이미 전 요청에 `X-Installation-Id`를 보내므로 요청 형태 변경 없음. 기기별 동작(기기 B 전부 꺼짐) 검증은 BE 변경이 dev에 배포된 뒤 실측한다.
- **토큰 등록 시점 이동(BE KB-543, kbap-server#260 draft→develop, 2026-09-11 통보)**: `PUT /api/notifications/tokens`는 회원 전용(Authorization 없으면 401, 서버 호환 처리 없음). FE는 회원 세션이 있을 때만 보내고 로그인 성공 직후 1회 등록한다(FR-020). 본문 `settings` 제거, 비회원 광고성 동의 UI 제거. 상세: kbap-server `kb-543-member-only-notification` 브랜치 `specs/kb-543-member-only-notification/contracts/notification-token.md`.
- **설정 단위 = BE KB-544 (2026-09-11 확정, 세부 계약 재공유 예정)**:
  - `GET/PATCH /api/notifications/settings` 경로 동일. **`X-Installation-Id` 필수**(누락 400 COMMON-002). **새 `X-API-Version` 매핑**으로 올리고 구 버전은 회원 단위 레거시 유지 → FE는 이 두 엔드포인트에 엔드포인트 한정 헤더(P-153 `RequestOpts.headers`)로 새 버전을 보낸다(버전 값은 확정 대기).
  - GET 응답 = 이 기기의 activity·mealTime·news 토글 + 회원의 동의 상태(두 문구 버전·동의 시각). PATCH는 이 기기 행만 변경.
  - news on = 회원 동의 원장에 열린 동의 보장(없거나 버전 다르면 두 버전 필수로 grant) + 이 기기 news=true. news off = 이 기기만 off. 회원의 모든 기기가 news off면 원장 동의를 닫는다. mealTime=true는 이 기기 news=true + 회원 열린 동의 필요(아니면 NOTIFICATION-001).
  - 발송은 기기 단위 판정(그 기기 토글 on + 광고성이면 회원 열린 동의). 로그아웃은 기기 설정 보존, 탈퇴는 기기별 소프트삭제. 토큰 등록은 설정 행을 만들지 않는다.
  - **기본값 = 전부 false** (BE 정정 2026-09-11, KB-466 규약 계승·KB-544 티켓 수정). 설정 행 없는 기기도 전부 false. 프라이머 허용 시 `activity:true` 저장 흐름(FR-013/018) 유지.
  - **스키마 현행 유지**(새 필드 없음): `{activity, news:{enabled, mealTime, privacyConsent, receiveConsent}}`. 의미만 변경 — `activity`·`news.mealTime` = 이 기기 저장값, `news.enabled` = 계산값(이 기기 news 저장값 AND 회원 열린 동의 2종 유효), `privacyConsent`·`receiveConsent` = 회원 단위. PATCH 본문도 현행 유지. `X-API-Version` 값은 KB-544 착수 시 확정(앱 릴리스 번호 규약, 현재 최대 2.0) → FE는 상수 1곳.
- 토큰 API `PUT /api/notifications/tokens`의 `lang` 필드는 이미 존재하고 FE도 이미 보내고 있다(앱 시작·언어 변경 시). 추가 계약 변경 없음.

## Assumptions

- 알림 기능은 회원 전용이다(2026-09-08 결정). 게스트용 로컬 동의 저장소는 이 작업에서 제거되며 마이그레이션하지 않는다(게스트 동의는 서버에 기록된 적이 없으므로 보존할 법적 기록이 없다). 토큰 API의 게스트 `settings` 필드는 사용하지 않는다.
- 기존 로컬 3토글 값은 서버로 이관하지 않는다. 서버 기본값(전부 꺼짐)에서 시작하며, 회원은 필요 시 다시 켠다. 광고성 동의는 어차피 서버에 버전·시각이 기록되어야 하므로 로컬 값을 승계할 수 없다.
- 기존 프라이머 노출 기록(`kbap.push.prompted.v1`)이 있는 기기는 스캔 프라이머 시트가 다시 뜨지 않는다. "나중에" 쿨다운 재노출(UX 리서치 권고)은 이번 범위 밖 — 후속 티켓.
- 알림 문구(제목·본문)는 전부 서버가 구성한다. 앱은 수신 페이로드를 그대로 표시하며 문구 리소스를 갖지 않는다(KB-498 data 계약 범위).
- 「활동 푸시」 하나로 리뷰 반응과 리뷰 리마인더를 통합한다. 개별 세분 토글은 범위 밖.
- 동의 문구 개정으로 버전이 오를 때 기존 동의자에게 재동의를 요구하는 흐름은 범위 밖. 서버 저장 상태를 그대로 보여준다.
- 화면이 보내는 요청은 `activity`, `news.enabled:true`(+버전 2종, 시트 확인), `news.enabled:false`(소식 토글 OFF), `news.mealTime` 네 가지. 동의 원장 철회는 서버 규칙(KB-544)에 따르며 FE는 관여하지 않는다.
- 발송 시간대 안내 문구·철회 안내 문구는 화면에 두지 않는다(2026-09-11 삭제).
- 서버 설정 API는 이미 개발 서버에 배포되어 있고 계약이 확정되어 있다(선행 작업 완료). 푸시 토큰 등록 작업(직전 PR)은 머지되었다.
- 회원의 현재 언어는 기존 앱 언어 설정을 따른다. 설정 화면에서 언어를 바꾸는 기능은 없다.
- 알림함(수신 목록) 화면은 이 작업과 무관하다.
