# Feature Specification: 푸시 알림 데이터 계약 반영 — 유형 개명·신설, 알림 id 전달, Android 알림 채널

**Feature Branch**: `002-push-data-contract`

**Created**: 2026-09-11

**Status**: Draft

**Input**: User description: "498 워크트리" — Jira KB-498 「[FE] 푸시 data 계약 반영 — NUDGE→SCAN_SUGGESTION 개명·notificationId·Android 알림 채널」

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 서버가 보내는 다섯 가지 알림을 탭하면 맞는 화면으로 간다 (Priority: P1)

서버가 발송하는 푸시 알림은 다섯 유형이다. 리뷰 반응(HELPFUL), 스캔 제안(SCAN_SUGGESTION), 리뷰 리마인더(REVIEW_REMINDER), 소식(NEWS), 식사 시간(MEAL_TIME). 사용자가 알림을 탭하면 유형에 맞는 화면이 열린다(2026-09-12 종한 결정). 리뷰 리마인더는 해당 음식의 상세 화면. 소식과 식사 시간은 탭해도 앱만 열리고 특정 화면으로 이동하지 않는다. 리뷰 반응과 스캔 제안은 착지 기획이 미정이라 **임시 디버깅 화면("착지 미정, 기획 필요")**을 띄운다 — 기획 확정 시 교체.

**Why this priority**: 서버 계약이 바뀌어 기존 이름(NUDGE)의 알림은 더 이상 오지 않는다. 새 이름을 모르는 앱은 스캔 제안 알림을 탭해도 아무 화면도 열지 못한다. 식사 시간 알림은 신규 유형이라 같은 문제.

**Independent Test**: 다섯 유형의 알림 데이터를 각각 탭 시뮬레이션 → 기대 화면 경로가 나오면 통과. 알 수 없는 유형은 이동 없음.

**Acceptance Scenarios**:

1. **Given** 스캔 제안 알림 도착, **When** 탭, **Then** 임시 착지 화면(기획 필요, 유형 표시)이 열린다.
2. **Given** 식사 시간 알림 도착, **When** 탭, **Then** 앱만 열리고 화면 이동이 없다.
3. **Given** 리뷰 리마인더 알림(음식 id 포함) 도착, **When** 탭, **Then** 그 음식의 상세 화면이 열린다.
4. **Given** 리뷰 리마인더 알림에 음식 id가 없음, **When** 탭, **Then** 화면 이동이 없다.
5. **Given** 리뷰 반응 알림 도착, **When** 탭, **Then** 임시 착지 화면(기획 필요, 유형 표시)이 열린다.
6. **Given** 소식 알림 도착, **When** 탭, **Then** 앱만 열리고 화면 이동이 없다.
7. **Given** 앱이 모르는 유형의 알림 도착, **When** 탭, **Then** 화면 이동이 없고 오류도 없다.
8. **Given** 구 이름(NUDGE)의 알림이 도착(서버 롤백 등), **When** 탭, **Then** 알 수 없는 유형과 같이 무동작이다.

### User Story 2 - 알림함에 다섯 유형이 올바른 제목·본문으로 쌓인다 (Priority: P1)

푸시가 도착하면(앱이 앞에 있든 뒤에 있든) 앱 내 알림함에 한 줄로 기록된다. 각 유형은 사용자 언어로 된 제목과 본문을 갖는다. 스캔 제안·식사 시간·소식은 광고성이라 서버가 제목 앞에 "(광고)"와 본문 끝 수신거부 안내를 이미 붙여 보내므로 앱이 따로 붙이지 않는다.

**Why this priority**: 알림함 기록이 유형 이름에 묶여 있어 새 이름·신규 유형은 기록되지 않거나 빈 제목으로 쌓인다. 구 운영 공지(NOTICE) 유형은 폐기되어 소식(NEWS)으로 바뀐다.

**Independent Test**: 다섯 유형 알림을 도착시킨 뒤 알림함을 열어 각 줄의 제목·본문이 유형에 맞는 문구로 보이면 통과.

**Acceptance Scenarios**:

1. **Given** 스캔 제안 알림 도착, **When** 알림함 열람, **Then** 스캔 제안 제목·본문 문구가 사용자 언어로 보인다.
2. **Given** 식사 시간 알림 도착, **When** 알림함 열람, **Then** 식사 시간 제목·본문 문구가 보인다.
3. **Given** 소식 알림 도착, **When** 알림함 열람, **Then** 소식 제목·본문 문구가 보인다. 구 "환영" 공지 문구는 더 이상 쓰지 않는다.
4. **Given** 같은 알림이 두 번 관찰됨(도착 시와 탭 시), **When** 알림함 열람, **Then** 한 줄만 있다.
5. **Given** 앱이 모르는 유형의 알림 도착, **When** 알림함 열람, **Then** 기록되지 않는다.

### User Story 3 - 알림을 탭하면 서버 알림 id가 보존되어 읽음 처리로 이어질 수 있다 (Priority: P2)

서버는 모든 푸시에 기기 단위 알림 id를 실어 보낸다(같은 푸시라도 기기마다 id가 다르다). 사용자가 알림을 탭할 때 앱은 이동 경로와 함께 이 id를 넘겨받아, 후속 작업(알림함 서버 전환)에서 서버에 "읽음"을 알릴 수 있다. 이 작업에서는 id를 전달하는 통로만 만들고 읽음 호출은 하지 않는다.

**Why this priority**: id를 지금 버리면 후속 작업에서 탭 이벤트를 다시 뜯어야 한다. 통로만 열어 두면 후속은 호출 한 줄이다.

**Independent Test**: id가 포함된 알림 탭 → 콜백에 id가 전달됨. id 없는 알림 탭 → 콜백에 id 없음(정의되지 않음)으로 전달되고 이동은 정상.

**Acceptance Scenarios**:

1. **Given** 알림 데이터에 알림 id가 있음, **When** 탭, **Then** 이동 경로와 그 id가 함께 전달된다.
2. **Given** 알림 데이터에 알림 id가 없음(구 서버·로컬 알림), **When** 탭, **Then** 이동 경로만 전달되고 id는 비어 있다.
3. **Given** 앱이 종료된 상태에서 알림 탭으로 시작, **When** 앱 부팅 완료, **Then** 그 알림의 경로와 id가 1회 전달된다.

---

### User Story 4 - Android에서 푸시가 헤드업 배너로 뜬다 (Priority: P2)

Android 사용자에게 푸시가 도착하면 화면 상단에 소리와 함께 헤드업 배너가 뜬다. 현재는 알림 채널 중요도가 기본이라 상태바 아이콘만 조용히 생길 수 있다.

**Why this priority**: 리뷰 리마인더·식사 시간 같은 시점성 알림은 눈에 띄지 않으면 의미가 없다. 서버는 이미 최고 우선순위·기본 소리로 보내고 있어 앱 쪽 채널 설정만 빠져 있다. 채널은 활동 알림과 광고성 소식 두 개로 나눠 사용자가 기기 설정에서 광고성만 따로 끌 수 있게 한다(2026-09-12 결정). 채널 중요도는 만든 뒤 바꿀 수 없으므로 `default` 채널은 만들지 않는다.

**Independent Test**: Android 실기기에서 푸시 수신 시 헤드업 배너와 소리가 나오면 통과. iOS는 변화 없음.

**Acceptance Scenarios**:

1. **Given** Android 기기, 앱 첫 실행 후, **When** 서버가 유형에 맞는 채널(활동=`activity`, 광고성=`news`)로 푸시를 보내면, **Then** 상단 헤드업 배너와 소리로 표시된다. 서버가 아직 `default`로 보내면 기존과 같이 조용히 표시된다(회귀 없음).
2. **Given** iOS 기기, **When** 앱 실행, **Then** 채널 설정 동작이 일어나지 않고 기존 동작 그대로다.
3. **Given** 푸시 기능 플래그가 꺼진 빌드, **When** 앱 실행, **Then** 알림 라이브러리 호출(채널 설정 포함)이 전혀 없다.

---

### Edge Cases

- 알림 데이터의 유형 값이 대소문자만 다르거나 공백이 붙어 오면 알 수 없는 유형으로 취급한다(정확 일치만).
- 음식 id가 숫자로 오든 문자열로 오든 리뷰 리마인더 경로는 같게 만들어진다.
- 알림 id가 문자열로 오면(서버 직렬화 차이) 그대로 전달하되 숫자로 강제 변환하지 않는다. 후속 작업이 처리한다.
- 앱이 앞에 있을 때 도착한 알림도 알림함에 기록되고, 그 뒤 탭하면 중복 기록 없이 이동만 한다.
- 알림 채널 설정이 실패해도(권한·OS 차이) 앱 부팅과 알림 탭 처리는 정상 진행된다.
- 사용자가 언어를 바꾸면 이후 도착하는 푸시 문구는 서버가 결정하고, 앱은 토큰 재등록(이미 구현됨)으로 새 언어를 알린다. 이 작업은 그 동작이 유지되는지만 확인한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 앱이 인식하는 푸시 알림 유형은 정확히 다섯 가지여야 한다. HELPFUL, SCAN_SUGGESTION, REVIEW_REMINDER, NEWS, MEAL_TIME. 구 NUDGE·NOTICE는 인식하지 않는다.
- **FR-002**: 알림 탭 시 이동 경로는 유형별로 고정이어야 한다(2026-09-12 개정). REVIEW_REMINDER는 음식 id가 있을 때만 그 음식의 상세 화면, NEWS·MEAL_TIME·알 수 없는 유형은 이동 없음, HELPFUL·SCAN_SUGGESTION은 기획 확정 전까지 임시 착지 화면(`/push-landing?type=…`).
- **FR-003**: 알림 탭 콜백은 탭마다 항상 호출되어 이동 경로(없으면 null)와 서버 알림 id를 전달해야 한다. 이동 없는 유형(NEWS·MEAL_TIME 등)도 id는 전달한다(읽음 처리용). 데이터에 id가 없으면 정의되지 않음으로 전달한다. 루트 레이아웃은 경로가 있을 때만 이동한다.
- **FR-004**: 알림함 기록은 다섯 유형 각각에 사용자 언어 제목·본문 문구를 가져야 한다. 구 NUDGE·NOTICE 문구 키는 제거하고 SCAN_SUGGESTION·NEWS·MEAL_TIME 키로 대체한다.
- **FR-005**: 알림함 문구 키는 앱이 지원하는 10개 언어 모두에서 같은 키 집합이어야 한다.
- **FR-006**: 광고성 유형(SCAN_SUGGESTION·NEWS·MEAL_TIME)의 "(광고)" 접두와 수신거부 안내는 서버가 붙인다. 앱은 푸시 제목·본문을 가공하지 않는다.
- **FR-007**: Android에서는 앱이 알림 탭 구독을 시작할 때 알림 채널 두 개를 1회 설정해야 한다. `activity`(활동 알림: HELPFUL·REVIEW_REMINDER, 최고 중요도)와 `news`(K-Bap 소식: SCAN_SUGGESTION·NEWS·MEAL_TIME, 높은 중요도). 채널 이름은 설정 화면 그룹명 문구를 재사용한다(하드코딩 금지). `default` 채널은 만들지 않는다. iOS에서는 아무 동작도 하지 않는다.
- **FR-008**: 푸시 기능 플래그가 꺼진 빌드에서는 채널 설정을 포함한 알림 라이브러리 호출이 전혀 없어야 한다(기존 정적 import 금지 규약 유지).
- **FR-009**: 기존 딥링크 매핑 테스트는 다섯 유형 + 알 수 없는 유형 + 구 이름(NUDGE) 무동작 케이스를 포함해야 한다.
- **FR-010**: 로컬 리뷰 리마인더 예약에 쓰는 OS 예약 id 저장소는 이 작업과 무관하며 변경하지 않는다.

### Key Entities

- **푸시 알림 데이터**: 서버가 푸시에 싣는 구조화 데이터. 유형(5종 중 하나) · 음식 id(리뷰 리마인더만, 선택) · 서버 알림 id(항상, 기기 단위).
- **알림함 항목**: 기기에 기록되는 한 줄. 중복 방지 키 · 제목 문구 키 · 본문 문구 키 · 도착 시각 · 읽음 여부 · 원본 데이터(유형·음식 id).
- **알림 채널(Android)**: `activity`·`news` 두 채널. 이름과 중요도를 가진다. 서버는 유형별로 이 채널 id를 실어 발송한다(BE KB-469·470·471·474에 반영, 파이프라인 KB-468 코멘트).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 다섯 유형 + 알 수 없는 유형 + 구 이름의 탭 경로 매핑이 유닛 테스트에서 100% 기대값과 일치한다.
- **SC-002**: 다섯 유형 알림이 알림함에 빈 제목 없이 기록되고, 10개 언어 문구 키 집합이 일치한다(자동 검사 통과).
- **SC-003**: 알림 id가 있는 탭 100%에서 콜백에 id가 전달되고, 없는 경우 정의되지 않음으로 전달된다.
- **SC-004**: Android 실기기에서 푸시 수신 시 헤드업 배너·소리가 확인된다. iOS 동작 변화 0.
- **SC-005**: 플래그 꺼진 빌드의 알림 라이브러리 호출 0회(기존 폭탄 목 테스트 통과).
- **SC-006**: 타입 검사 0 오류, 전체 테스트 통과. 변경은 JS 전용이라 OTA로 배포 가능.

## Assumptions

- 서버 계약은 확정 상태다(2026-09-11 갱신분 기준). 유형 5종, 알림 id 항상 포함.
- 서버 알림 id의 실제 사용(읽음 처리 호출)은 후속 작업 범위다. 이 작업은 전달 통로만 만든다.
- 알림함은 아직 기기 로컬 저장이다. 서버 알림함 전환은 후속 작업이며, 그때 로컬 문구 키는 서버 문자열로 대체될 수 있다.
- 구 이름 알림(NUDGE·NOTICE)에 대한 호환 처리는 하지 않는다. 서버가 더 이상 보내지 않는다.
- 알림 설정 화면 재편(KB-497)은 #148로 먼저 머지됐다. 이 작업은 그 위에서 같은 10개 언어 파일의 `inbox` 블록만 건드린다.
- 푸시 언어는 토큰 등록 시 보고한 언어로 서버가 결정한다. 언어 변경 시 토큰 재등록은 이미 구현되어 있어 유지 확인만 한다.
