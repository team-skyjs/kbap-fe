## Clarifications

- Q: 주문 상세의 항목별 리뷰 작성 진입을 어떤 형태로 넣나? → A: B안 — 현재대로 유지(행 탭 = 음식 상세, 그 안에서 리뷰 작성). 별도 버튼·직행 변경 없음.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 리마인더 푸시를 탭하면 그 주문의 상세가 열린다 (Priority: P1)

주문 완료 약 1시간 뒤 서버가 보내는 "아까 그 메뉴 어땠어요?" 알림을 탭하면, 그 주문의 상세 화면이 열린다. 지금은 음식 하나의 상세로 갔지만, 리마인더는 이제 주문 단위로 오므로 주문 상세가 착지다. 앱이 꺼져 있었으면 주문 상세로 시작하고, 다른 화면에 있었으면 그 위에 열린다.

**Why this priority**: 서버 배치가 켜지는 순간부터 리마인더에는 음식 id가 실리지 않는다. 앱이 주문 id를 읽지 못하면 리마인더를 탭해도 앱만 켜지고 아무 데도 가지 않아 리마인더의 목적(리뷰 유도)이 사라진다.

**Independent Test**: 관리자 테스트 발송으로 주문 id가 실린 리마인더 알림을 보낸 뒤, 백그라운드 상태와 종료 상태에서 각각 탭 → 두 경우 모두 그 주문의 상세 화면이 열리면 통과.

**Acceptance Scenarios**:

1. **Given** 앱 백그라운드, 아무 화면, **When** 주문 id가 실린 리마인더 알림 탭, **Then** 그 주문의 상세 화면이 열리고 뒤로 가기가 동작한다.
2. **Given** 앱 종료 상태, **When** 리마인더 알림 탭, **Then** 앱이 시작되고 그 주문의 상세 화면이 표시된다.
3. **Given** 주문 상세가 이미 맨 위(같은 주문), **When** 같은 리마인더를 다시 탭, **Then** 화면이 두 장 쌓이지 않는다. 다른 주문의 리마인더면 그 주문으로 내용이 바뀐다.
4. **Given** 리마인더 알림에 주문 id가 없거나 숫자가 아님, **When** 탭, **Then** 아무 데도 이동하지 않고 앱만 켜진다(오착지 금지).
5. **Given** 리마인더 알림에 옛 방식의 음식 id만 실림(구 로컬 알림 잔존), **When** 탭, **Then** 이동하지 않는다. 음식 상세로 가는 분기는 더 이상 없다.

---

### User Story 2 - 알림함에서 리마인더 항목을 탭해도 같은 주문 상세로 간다 (Priority: P1)

알림함 목록의 리마인더 항목을 탭하면 읽음 처리와 함께 푸시 탭과 같은 주문 상세가 열린다. 서버가 알림함 응답에 주문 id를 실어 주며, 리마인더가 아닌 유형에는 주문 id가 없다.

**Why this priority**: 푸시를 놓친 사용자가 알림함에서 리마인더를 되찾는 경로다. 푸시 탭과 알림함 탭의 착지가 다르면 사용자가 혼란스럽고, 옛 음식 id 필드는 항상 비어 있어 기존 경로는 이제 어디로도 가지 않는다.

**Independent Test**: 알림함에 리마인더 항목이 있는 상태에서 탭 → 읽음으로 바뀌고 그 주문의 상세가 열리면 통과. 다른 유형 항목은 기존 착지 그대로.

**Acceptance Scenarios**:

1. **Given** 알림함에 주문 id가 있는 미읽음 리마인더 항목, **When** 탭, **Then** 항목이 읽음으로 바뀌고 그 주문의 상세가 열린다. 이동은 읽음 응답을 기다리지 않는다.
2. **Given** 알림함의 리마인더 항목에 주문 id가 없음(서버 전환 이전 행), **When** 탭, **Then** 읽음 처리만 하고 알림함에 머문다.
3. **Given** 알림함의 다른 유형 항목(도움돼요·식사 시간·스캔 제안·소식), **When** 탭, **Then** 기존 착지 그대로이며 주문 id 유무에 영향받지 않는다.
4. **Given** 알림함 응답에 옛 음식 id 필드가 값과 함께 옴, **When** 리마인더 항목 탭, **Then** 그 값은 무시된다(주문 id만 판단).

---

### User Story 3 - 주문 완료 시 기기에 리마인더를 예약하지 않는다 (Priority: P1)

주문 완료 후 앱이 기기에 "1시간 후 리뷰" 로컬 알림을 걸어 두던 동작을 없앤다. 서버 배치가 같은 시점에 같은 내용을 보내므로, 둘 다 살아 있으면 사용자는 1시간 뒤 리마인더를 두 번 받는다.

**Why this priority**: 중복 알림은 광고성 알림 피로와 같은 계열의 신뢰 손상이다. 서버 배치를 켜는 시점이 이 앱 버전 릴리스에 맞춰지므로, 이 버전에서 로컬 예약이 반드시 꺼져 있어야 한다.

**Independent Test**: 주문 완료 흐름을 끝까지 진행한 뒤 기기의 예약 알림 목록을 확인 → 리마인더 예약이 0건이면 통과. 리뷰 작성 완료 시에도 오류 없이 진행되면 통과.

**Acceptance Scenarios**:

1. **Given** 알림 권한 허용·활동 알림 설정 켜짐(예약 조건이 모두 충족되는 상태), **When** 주문 완료 모달을 닫음, **Then** 기기에 리마인더 예약이 생기지 않는다.
2. **Given** 이전 버전에서 걸어 둔 리마인더 예약이 기기에 남아 있음, **When** 새 버전으로 갱신 후 앱 실행, **Then** 남은 예약은 그대로 발화되어도 탭 시 이동하지 않는다(스토리 1 시나리오 5). 앱이 남은 예약을 찾아 지우지는 않는다.
3. **Given** 리뷰 작성 완료, **Then** 로컬 예약 취소 호출이 없어도 흐름이 정상 종료된다.

---

### User Story 4 - 착지한 주문 상세에서 항목별로 리뷰 작성에 들어간다 (Priority: P2)

리마인더는 주문 단위로 오므로, 주문 상세에서 각 음식 항목을 탭해 음식 상세로 들어가고 거기서 리뷰를 작성한다(현재 동작 유지, 2026-09-28 종한 확정 B안). 아직 준비 중인 항목(서버가 준비되지 않았다고 표시)과 음식 id가 없는 항목은 탭이 비활성이다.

**Why this priority**: 리마인더의 최종 목적은 리뷰 작성이다. 주문 상세 항목 행 → 음식 상세 → 리뷰 작성 경로가 이미 존재하므로 새 진입 요소를 추가하지 않는다. 이 스토리는 착지 후 경로가 끊기지 않았음을 확인하는 회귀 범위다.

**Independent Test**: 항목 3개(준비 완료 2·준비 중 1)인 주문 상세를 열어, 준비 완료 항목 탭이 음식 상세로 가고 준비 중 항목은 비활성이며, 음식 상세에서 리뷰 작성으로 진입 가능하면 통과.

**Acceptance Scenarios**:

1. **Given** 준비 완료 항목, **When** 항목 행을 탭, **Then** 그 음식의 상세로 이동하고 거기서 리뷰 작성에 진입할 수 있다.
2. **Given** 준비 중 항목(ready=false), **Then** 행이 비활성으로 보이고 눌러도 이동하지 않는다.
3. **Given** 음식 id가 없는 항목(미매칭), **Then** 행이 비활성이다.

---

### Edge Cases

- 리마인더 알림에 주문 id가 문자열 숫자("12")로 오면 숫자와 동일하게 취급한다. 숫자로 해석되지 않으면 이동하지 않는다.
- 주문 id가 매우 큰 값(64비트 정수 범위)이어도 정밀도 손실 없이 주문 상세 경로를 만든다.
- 리마인더가 가리키는 주문이 서버에서 사라졌거나 다른 계정의 주문이면 주문 상세 화면의 기존 오류·빈 상태 처리가 담당한다. 착지 로직은 별도 검증을 하지 않는다.
- 게스트 상태(로그아웃)에서 리마인더를 탭하면 주문 상세 화면의 기존 회원 게이트가 처리한다.
- 앱 종료 상태에서 탭으로 시작할 때 온보딩 미완료면 온보딩이 우선이다(기존 원칙).
- 알림함 응답에 주문 id 필드 자체가 없는 구 응답이 와도 목록 렌더가 깨지지 않는다.
- Android에서 리마인더는 기존 활동 채널로 도착한다. 새 채널을 만들지 않으므로 사용자의 기존 채널 설정(끔 포함)이 그대로 적용된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 리마인더(REVIEW_REMINDER) 알림 탭은 알림 데이터의 주문 id로 주문 상세 화면으로 이동해야 한다. 주문 id가 없거나 숫자로 해석되지 않으면 이동하지 않는다.
- **FR-002**: 리마인더 알림 데이터의 음식 id로 음식 상세로 가던 분기를 제거해야 한다. 음식 id만 실린 리마인더는 이동하지 않는다.
- **FR-003**: 알림함 목록·읽음 응답의 주문 id(없을 수 있음)를 읽어 리마인더 항목 탭 시 푸시 탭과 같은 주문 상세로 이동해야 한다. 응답의 옛 음식 id 필드는 판단에 쓰지 않는다.
- **FR-004**: 알림함의 리마인더 외 유형 착지(도움돼요=내 리뷰, 식사 시간·스캔 제안=홈, 소식=이동 없음)는 변하지 않아야 한다.
- **FR-005**: 주문 완료 시 기기에 리마인더 로컬 알림을 예약하는 동작을 제거해야 한다. 예약 조건이 모두 충족되어도 예약이 생기지 않는다.
- **FR-006**: 리뷰 작성 완료 시 로컬 리마인더 예약을 취소하던 동작을 제거해야 하며, 제거 후에도 리뷰 작성 흐름이 정상 종료되어야 한다.
- **FR-007**: 주문 상세의 각 항목 행 탭은 음식 상세로 이동해야 하며(현재 동작 유지), 서버가 준비 중(ready=false)으로 표시한 항목과 음식 id가 없는 항목은 비활성이어야 한다. 새 리뷰 진입 요소는 추가하지 않는다.
- **FR-008**: (삭제 — B안 채택으로 주문 상세 레이아웃 변경 없음)
- **FR-009**: Android 알림 채널은 기존 활동(activity) 채널을 그대로 쓰며 새 채널을 만들지 않아야 한다.
- **FR-010**: 백그라운드 탭과 앱 종료 상태 탭 두 경로에서 같은 주문 상세에 도달해야 한다. 같은 주문 상세가 이미 맨 위면 재사용하고 새로 쌓지 않는다.
- **FR-011**: 유형별 착지 테스트에 리마인더 주문 id 있음·없음·숫자 아님·음식 id만 있음 케이스를 포함해야 하며, 로컬 예약 제거 테스트는 예약 조건 충족 상태에서 예약이 발생하지 않음을 확인해야 한다.
- **FR-012**: 기존 푸시 데이터 계약 명세(specs/002)와 푸시 탭 착지 명세(specs/005)의 리마인더 행을 이 결정(주문 상세·주문 id)으로 갱신해야 한다.

### Key Entities

- **리마인더 알림 데이터**: 유형(REVIEW_REMINDER)·주문 id(숫자, 64비트 정수)·알림 id. 서버 배치가 주문 저장 60~65분 뒤 발송. 음식 id는 더 이상 실리지 않는다.
- **알림함 항목**: 기존 속성(id·제목·본문·도착 시각·읽음·유형)에 주문 id(리마인더만, 그 외 없음)가 추가된다. 옛 음식 id 필드는 항상 비어 있다.
- **주문 항목**: 음식 id(없을 수 있음)·준비 여부(ready)를 가지며, 음식 상세(→리뷰 작성) 진입 활성 여부를 결정한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 착지 매핑 유닛에서 리마인더 4케이스(주문 id 있음·없음·숫자 아님·음식 id만) + 기존 유형 전부가 100% 기대와 일치한다.
- **SC-002**: 주문 완료 흐름을 거친 뒤 기기의 예약 알림에 리마인더가 0건이다.
- **SC-003**: 리마인더 푸시와 알림함 항목이 실기기(iOS·Android) 백그라운드·종료 두 경로 모두에서 해당 주문 상세에 도달한다.
- **SC-004**: 주문 상세에서 준비 완료 항목 탭이 음식 상세에 도달하고, 준비 중 항목은 탭해도 이동이 0건이다(기존 회귀 유지).
- **SC-005**: 타입 검사 0 오류, 전체 테스트 통과.

## Assumptions

- 주문 상세 화면은 이미 존재하며(profile/order/{id}) 회원 게이트·오류·빈 상태 처리를 자체 보유한다. 착지 로직은 경로만 만든다.
- 알림함 응답의 주문 id는 정수로 오며, 앱은 주문 상세 경로에 문자열로 실어 정밀도를 보존한다.
- 이전 버전이 기기에 남긴 로컬 리마인더 예약은 능동적으로 정리하지 않는다. 최대 1회, 1시간 안에 자연 소멸하며 탭해도 이동하지 않는다.
- 활동 알림 설정(activity)을 끈 사용자는 서버가 리마인더를 보내지 않는다고 가정한다(서버 설정 정본, P-147). 앱은 로컬에서 별도 필터를 두지 않는다.
- 리마인더 문구(제목·본문)는 서버가 발송 시점 기기 언어로 만든다. 앱의 로컬 리마인더 문구 키는 다른 용도가 없으면 제거 대상이다.
- 서버 배치의 prod 활성화는 이 앱 버전 릴리스에 맞춘다. **릴리스 일정은 서버 팀에 별도로 회신해야 하는 열린 항목**이며 이 명세의 범위 밖이다.
- 이 변경은 네이티브 소스를 건드리지 않으므로(채널 추가 없음) OTA 배포 가능하다. 단 로컬 예약 제거는 중복 알림 방지를 위해 서버 배치 활성화 전에 사용자 기기에 도달해 있어야 한다.
