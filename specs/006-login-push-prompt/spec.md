# Feature Specification: 첫 설치 로그인 화면에서 OS 알림 권한 즉시 요청

**Feature Branch**: `006-login-push-prompt`

**Created**: 2026-09-22

**Status**: Draft

**Input**: User description: "스캔하러 들어가면 카메라 접근 허용을 물어보면서 아이폰 설정 앱에 카메라 토글이 생긴다. 이처럼 첫 설치 후 스플래시 직후 로그인 화면이 나오는 시점에 알림 권한을 묻는 창을 강제로 띄워서 선택하도록 한다." — Jira KB-631 「[FE] 첫 설치 로그인 화면 진입 시 OS 알림 권한 팝업 즉시 요청 — 카메라 권한과 같은 방식」

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 처음 설치한 사용자가 로그인 화면에서 알림 권한을 결정한다 (Priority: P1)

앱을 처음 설치해 실행하면 스플래시 뒤 로그인 화면이 뜨고, 그 위에 OS 알림 권한 팝업이 바로 나타난다. 사용자는 허용 또는 거부를 고른다. 어느 쪽을 골라도 기기 설정 앱에 K-Bap 알림 항목이 생긴다. 이후 앱 사용 중 이 팝업은 다시 뜨지 않는다.

**Why this priority**: 지금은 권한 요청이 첫 스캔 결과 화면에만 있어서 스캔을 안 한 회원은 권한이 "물어본 적 없음"으로 남고 푸시가 한 건도 오지 않는다(9/22 실측). 카메라 권한처럼 진입 시점에 물어 상태를 확정하면 이 구멍이 사라진다. 첫 스캔 우선 결정(9/11)을 뒤집는 명시적 결정이다.

**Independent Test**: 앱 삭제 → 설치 → 실행 → 스플래시 뒤 로그인 화면에서 OS 알림 팝업이 뜨고, 허용 또는 거부 후 기기 설정 앱에 K-Bap 알림 항목이 보이면 통과.

**Acceptance Scenarios**:

1. **Given** 처음 설치한 기기, **When** 스플래시가 끝나고 로그인 화면이 표시됨, **Then** OS 알림 권한 팝업이 즉시 뜬다.
2. **Given** 팝업 표시, **When** 허용, **Then** 팝업이 닫히고 로그인 화면이 그대로 남아 있으며 기기 설정 앱에 알림 항목이 "허용"으로 생긴다.
3. **Given** 팝업 표시, **When** 거부, **Then** 팝업이 닫히고 로그인 화면이 그대로이며 기기 설정 앱에 알림 항목이 "꺼짐"으로 생긴다.
4. **Given** 팝업이 떠 있는 동안, **When** 사용자가 소셜 로그인 버튼을 누르려 함, **Then** 팝업이 먼저 처리되어야 하고 팝업 뒤 로그인 흐름은 정상이다(팝업이 로그인 버튼 동작을 깨지 않는다).
5. **Given** 팝업에서 결정을 마침, **When** 같은 세션에서 로그인 화면으로 다시 옴(게스트 진입 후 게이트 → 로그인), **Then** 팝업이 다시 뜨지 않는다.
6. **Given** 재설치, **When** 첫 실행 로그인 화면, **Then** OS가 이전 결정을 기억하고 있으면 팝업이 뜨지 않고, 기억이 없으면 뜬다(OS 정책 그대로, 앱은 요청만 한다).

---

### User Story 2 - 허용한 사용자는 로그인하면 바로 푸시를 받을 수 있다 (Priority: P1)

로그인 화면에서 알림을 허용한 사용자가 소셜 로그인을 마치면, 별도 조작 없이 이 기기의 푸시 토큰이 서버에 등록되어 푸시를 받을 수 있는 상태가 된다.

**Why this priority**: 권한만 얻고 토큰이 등록되지 않으면 여전히 푸시가 오지 않는다. 토큰 등록은 회원 전용이라 로그인 완료 시점에 이어져야 한다.

**Independent Test**: 로그인 화면 팝업 허용 → 소셜 로그인 완료 → 서버에 이 기기의 토큰 행이 생기면 통과.

**Acceptance Scenarios**:

1. **Given** 로그인 화면에서 알림 허용, **When** 소셜 로그인 성공, **Then** 이 기기의 푸시 토큰이 서버에 등록된다.
2. **Given** 로그인 화면에서 알림 거부, **When** 소셜 로그인 성공, **Then** 토큰 등록을 시도하지 않고 알림 설정 화면에는 "기기 설정 열기" 안내가 보인다.
3. **Given** 게스트 상태(로그인 전), **When** 팝업 허용, **Then** 서버에는 아무 요청도 가지 않는다(토큰 등록은 회원 전용).

---

### User Story 3 - 기존 알림 안내들과 중복되지 않는다 (Priority: P2)

로그인 화면에서 이미 권한을 결정한 사용자에게는 첫 스캔 결과의 알림 안내 시트가 뜨지 않는다. 알림 설정 화면은 결정된 상태(허용/거부)에 맞는 모습을 보인다.

**Why this priority**: 같은 질문을 두 번 받으면 사용자가 앱을 신뢰하지 않게 된다. 스캔 안내 시트와 설정 화면 배너는 이 팝업을 못 본 기기(구버전에서 올라온 사용자 등)를 위한 후순위 경로로 남긴다.

**Independent Test**: 로그인 화면에서 허용 또는 거부 → 첫 스캔 결과 화면에 알림 안내 시트가 뜨지 않으면 통과.

**Acceptance Scenarios**:

1. **Given** 로그인 화면 팝업에서 허용, **When** 첫 스캔 결과, **Then** 알림 안내 시트가 뜨지 않는다.
2. **Given** 로그인 화면 팝업에서 거부, **When** 첫 스캔 결과, **Then** 알림 안내 시트가 뜨지 않는다(OS 팝업은 1회성이라 다시 물어도 소용없다).
3. **Given** 로그인 화면 팝업에서 거부, **When** 알림 설정 화면 진입, **Then** "기기 설정에서 알림이 꺼져 있어요 / 기기 설정 열기" 배너가 보인다.
4. **Given** 이 앱 버전으로 업데이트한 기존 사용자(재설치 아님), **When** 실행, **Then** 로그인 화면 팝업 경로는 타지 않고 기존 경로(스캔 안내·설정 배너)가 그대로 동작한다.

---

### Edge Cases

- 스플래시 게이트(세션 복구·잔존 정리)가 끝나기 전에 팝업을 띄우면 안 된다. 로그인 화면이 실제로 보이는 시점 이후에 요청한다.
- 앱이 백그라운드로 갔다 돌아오는 동안 팝업이 걸쳐 있어도 결과 처리는 한 번만 일어난다.
- 팝업 요청이 예외로 끝나면(권한 모듈 불가 등) 로그인 화면은 정상 진행되고, 다음 기회(스캔 안내·설정 배너)로 넘긴다.
- 푸시 기능 플래그가 꺼진 빌드에서는 팝업을 요청하지 않는다.
- 로그인 화면에 게이트에서 돌아오기(returnTo) 파라미터로 들어온 경우는 "첫 설치 첫 표시"가 아니므로 팝업을 띄우지 않는다.
- 접근성 도우미(VoiceOver) 사용 중에도 팝업은 OS 표준이라 별도 처리 없이 읽힌다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 처음 설치한 기기에서 로그인 화면이 첫 표시될 때 OS 알림 권한 팝업을 1회 요청해야 한다. 요청 시점은 스플래시 게이트 해소 뒤, 로그인 화면이 실제로 렌더된 뒤여야 한다.
- **FR-002**: 이 기기에서 이미 알림 안내에 응답한 기록(허용/거부)이 있으면 요청하지 않아야 한다.
- **FR-003**: 팝업 결과(허용/거부)를 이 기기의 알림 안내 응답 기록에 남겨, 첫 스캔 결과의 알림 안내 시트가 뜨지 않게 해야 한다.
- **FR-004**: 로그인 화면(게스트)에서는 팝업 결과와 무관하게 서버 요청을 보내지 않아야 한다. 허용한 사용자의 토큰 등록은 기존 로그인 성공 직후 경로가 담당한다.
- **FR-005**: 팝업이 로그인 버튼·게스트 진입 등 로그인 화면의 기존 동작을 방해하지 않아야 한다.
- **FR-006**: 게이트에서 돌아온 로그인 화면(returnTo 경유), 같은 세션의 재방문, 기존 사용자 업데이트에서는 팝업을 띄우지 않아야 한다.
- **FR-007**: 푸시 기능 플래그가 꺼진 빌드에서는 알림 라이브러리 호출이 없어야 한다(기존 정적 import 금지 규약 유지).
- **FR-008**: 팝업 결과 계측은 기존 권한 요청 함수 안의 계측(허용/거부)을 그대로 쓴다. 로그인 화면 전용 이벤트를 추가하지 않는다.
- **FR-009**: 알림 설정 화면과 첫 스캔 안내 시트의 기존 동작은 바뀌지 않는다. 이 팝업을 못 본 기기의 후순위 경로로 유지된다.
- **FR-010** *(플랜 단계 추가, 2026-09-22 — 서버 계약 실측)*: 서버의 활동 알림 설정(`activity`)은 기기별 기본값이 "꺼짐"이라, 로그인 화면 팝업에서 허용한 기기는 소셜 로그인 성공 직후 활동 알림을 1회 "켜짐"으로 저장해야 한다(기존 첫 스캔 안내 시트의 수락 경로와 동일한 기본값 적용). 이 적용은 기기당 1회뿐이며, 이후 사용자가 끈 값을 재로그인·계정 전환에서 되돌리지 않는다.

### Key Entities

- **알림 안내 응답 기록**: 이 기기에서 알림 권한 안내에 응답했는지(허용/거부/없음). 기기 로컬. 로그인 화면 팝업·스캔 안내 시트가 공유한다.
- **첫 설치 판별**: 앱 설치 후 첫 실행인지. 기존 잔존 정리 게이트가 판별한 값을 재사용한다.
- **OS 알림 권한 상태**: 허용/거부/미결정. OS가 정본이며 팝업은 미결정일 때만 실제로 표시된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 처음 설치한 기기 100%에서 로그인 화면 표시 직후 OS 알림 팝업이 뜨고, 결정 후 기기 설정 앱에 알림 항목이 생긴다(iOS 실기).
- **SC-002**: 같은 기기에서 팝업 요청은 최대 1회. 재방문·returnTo·기존 사용자 경로에서 0회(유닛).
- **SC-003**: 로그인 화면에서 허용한 사용자의 로그인 완료 직후 토큰 등록 요청 1회 + 활동 알림 켜짐 저장 1회가 발생한다(유닛 + 실기 서버 행 확인).
- **SC-004**: 로그인 화면에서 응답한 기기에서 첫 스캔 안내 시트 노출 0회(유닛).
- **SC-005**: 플래그 꺼진 빌드의 알림 라이브러리 호출 0(기존 잠금 테스트 통과).
- **SC-006**: 타입 검사 0 오류, 전체 테스트 통과. JS 전용이라 OTA 가능.

## Assumptions

- "첫 설치"는 기존 잔존 정리 게이트가 세우는 설치 센티널로 판별한다. 재설치는 첫 설치로 취급하되, OS가 권한을 기억하면 팝업은 OS가 생략한다.
- 팝업 앞에 앱 자체 안내(프라이머)를 두지 않는다. 카메라 권한과 같은 방식으로 OS 팝업만 띄운다. 안내 문구가 필요해지면 별도 결정.
- 알림 안내 응답 기록은 스캔 안내 시트와 같은 저장소를 쓴다. 로그인 화면에서 응답하면 스캔 시트는 자연히 생략된다.
- 광고성 동의(소식)는 이 팝업과 무관하다. 여전히 알림 설정 화면의 동의 시트에서 받는다.
- 로그인 화면 진입 시점에 사용자는 게스트다. 토큰 등록은 로그인 성공 직후 기존 경로가 처리하며, 이 작업은 그 경로를 바꾸지 않는다.
- 첫 스캔 우선 결정(9/11 UX 리서치 B안)은 이 작업으로 폐기된다. 관련 명세(specs/001)의 해당 항목은 참고용으로 남긴다.
